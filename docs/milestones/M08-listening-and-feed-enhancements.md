## Outcome and scope boundary

Make the existing archive easier to share, control from device media surfaces, and navigate in podcast clients, and make ordinary playback work on the owner's iPad running Safari 14.3. Deliver exactly these five areas:

All five areas are milestone completion requirements. They can ship as independently reviewed changes; one feature's release does not declare the whole milestone complete. Browser-specific optional Media Session support is not a requirement for Safari 14.3 playback.

## Contracts to preserve

- Fresh documents and shared links start paused. Shared timestamps take precedence over restoration, but must not bypass the confirmation required when a user navigates away from active playback within the site. Seek only after the selected media is ready; ignore stale results after selection changes.
- Keep the [timestamp precision rule](../CONTENT.md#episode-fields-and-new-episodes): preserve canonical fractional seconds and truncate toward the earlier time in any lower-precision output. Share URLs and chapters must use the same audio timeline as the existing tracklist.
- Reuse the current player for Media Session actions. No second audio element, independent queue, or new interpretation of previous/next track is required. Keep episode metadata available for untimed and empty tracklists; detailed metadata follows the active track where known. Feature-detect optional APIs and actions individually.
- Safari work must address both the entry-loading failure and other runtime compatibility gaps exposed after startup. The [September 18 diagnosis](../operations/acceptance-2026-09-18.md#ipad-safari-observation) identifies an import-map dependency; removing it alone is not proof that Safari 14.3 works. Preserve the original-MP3 Safari path and existing Chromium virtual-MP4 behavior.
- Chapter documents use the [Podcast Namespace JSON chapters format](https://github.com/Podcastindex-org/podcast-namespace/blob/main/docs/examples/chapters/jsonChapters.md), which supports fractional `startTime` values and the `application/json+chapters` media type. Do not embed chapters into or rewrite audio files. Use a published-episode endpoint and the existing publication predicate; draft and unknown episode chapter requests must not reveal metadata.
- Feed validators must account for the new output. Timed-track edits that change chapters must invalidate the chapter representation; artwork or chapter-reference changes must invalidate the feed representation. Cache expiry must permit clients to observe corrections after the corrected content is deployed, without changes to subscriber identity.
- Current inventory is 34 fully timed episodes / 626 timed tracks, 16 untimed tracklists / 206 tracks, and five missing lists. Chapter acceptance uses available timing data; researching missing data is not a dependency. Add boundary fixtures for partial timing rather than assuming every future list is complete.
- Preserve keyboard operation, labels, focus, responsive layout, and reduced-motion behavior in changed controls. The separately deferred assistive-technology audit is not added to this milestone.

## Reviewable implementation sequence

1. **Safari startup and playback:** establish the compatibility baseline and real iPad acceptance first, so subsequent enhancements build on working playback.
2. **Timestamp sharing:** resolve the URL grammar, exact validation/precedence rules, and copy-control placement in the implementation plan, then deliver the feature and navigation regressions.
3. **Media Session:** define the action/metadata transition table against the existing controller and verify supported device controls. The [Media Session specification](https://www.w3.org/TR/mediasession/) is the interface reference; platform UI availability is recorded rather than assumed.
4. **Feed enhancements:** add item artwork and chapter documents/references, with feed/endpoint tests and Podcast Addict acceptance. Split artwork and chapters into separate PRs if the combined review becomes unwieldy.

Before coding, expand these slices into an implementation-grade plan using the roadmap's planning checklist, with exact repository targets and behavior tests. Run the canonical `pnpm verify` gate for implementation and document manual device/client evidence. Keep one PR open at a time; later work may proceed on local forward branches. Reviews run automatically on pushes; do not post PR status commentary or request reviews. Release decisions remain separate from this documentation update.
