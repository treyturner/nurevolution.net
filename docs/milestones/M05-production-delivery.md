## Delivery architecture

### Application image and release identity

Use a small runtime Dockerfile that consumes the verified `.output/` artifact, pins a Node 22.23.2 base by digest, and starts `node .output/server/index.mjs`. Select and record the compatible base distribution/digest during implementation. Run as a dedicated non-root UID with a read-only filesystem, a bounded temporary directory if required, and an internal port. Exclude repository source, `.env`, dependencies used only for building, test fixtures, and bulk media from the image/build context. `.dockerignore` should allow only required image inputs.

Add a small `/api/health` endpoint that verifies the packaged catalog is readable and returns the release commit plus a healthy/unhealthy result. It must not fetch external media, reveal environment values, or replace full release acceptance with a liveness response. A malformed/missing catalog returns 503. Keep Docker health checks inexpensive and use bounded startup/readiness waits.

Every release record must include:

```text
schemaVersion, sourceCommit, verifyRunUrl, imageDigest, imageId,
configurationSha256, mediaManifestSha256, caddyBinarySha256, publishedAt
```

The image digest, configuration bundle, and media manifest form a deployable release together. `latest` and mutable commit tags may aid discovery but are never deployment inputs. Record previous/current releases per site and environment. Validate inputs as data and reject arbitrary image repositories, shell fragments, unknown environments, and missing matching configuration.

### Host, proxy, and site isolation

Host stack: Ubuntu 26.04 LTS x64 with Docker Engine and Compose, and Caddy handling public TLS, routing, and files. Inventory any existing edge proxy before installing one; do not compete for its ports or replace another site's service. Pin image/module versions and action revisions in implementation. Follow Docker's supported Ubuntu 26.04 installation path using its stable `resolute` repository, and account for Docker's firewall behavior when documenting exposure. [Docker on Ubuntu](https://docs.docker.com/engine/install/ubuntu/)

Use separate Compose project names, application networks, environment files, resource budgets, and release directories for each site. A suggested layout is `/srv/nurevolution/{releases,state,media,audit}` with separate shared-edge certificate/configuration storage. Keep private backups and secrets outside every served root. App containers have no Docker socket and no write access to media, certificates, or other sites. Caddy receives read-only asset mounts and persistent writable certificate storage.

Default to one active application container on the selected 1 GB host. Pull the candidate and validate its release/configuration/media inputs before stopping the current app; then start the candidate on the site's stable internal endpoint and use bounded readiness checks. Retain the previous image/configuration locally and restart it if candidate startup or acceptance fails, subject to the publication-identity rollback check below. Keep Caddy and persistent media serving throughout; app pages, APIs, and the feed can be briefly unavailable during replacement. Measure and record that interruption. Initial preview uses this same application slot before cutover; an always-running second preview instance is not part of the baseline.

Overlapping candidate/prior containers are an optional optimization only after measured peak usage proves the shared 1 GB host has sufficient headroom. If enabled, start and check the candidate before gracefully switching this site's upstream, then drain/stop the prior container. Do not make overlap a deployment prerequisite or claim zero downtime from configuration alone.

Per-site deployment must not restart the shared edge or unrelated containers. An operator-owned helper accepts only validated Nurevolution release records, locks against concurrent site deployments, modifies only this site's configuration, and validates the full edge configuration before reload. Pin SSH host keys and constrain deployment credentials to the chosen operation/transport. Resolve how GitHub-hosted runners reach the host before configuring firewall rules; do not disable host-key verification or silently broaden an existing access policy. [Caddy command/reload reference](https://caddyserver.com/docs/command-line)

Its versioned manifest contains the source commit, publication instant used, asset hash, and entries with `assetId`, `kind`, `sourceRoot`, `relativePath`, exact canonical URL/path, MIME type, length, SHA-256, and associated public episode slugs/download header where applicable.

- Artwork: `/home/coder/dev/net.nurevolution/wp/wp-content/uploads`.

The tool accepts those roots through explicit local arguments/configuration; it must not hard-code them into a deployed image. This is a transfer/integrity step using M0/M2 mappings, not another database import. Require all 156 baseline assets. Stage into a non-served location, verify destination hashes, then promote verified files. Never use a destructive sync or prune assets as part of application deployment.

Generate exact allowlisted routes from the manifest. The file server must not expose arbitrary uploaded files, directory listings, private manifests, dotfiles, backup data, or unpublished assets. Caddy does not make a served root a symlink sandbox; validate the staged tree and its ownership as well as request paths. ### HTTP and download contract

The table describes the confirmed Cloudflare website / DNS-only media arrangement. Attachment MIME behavior was refined by the implementation evidence below. Generate configuration safely as structured data or through a rigorously escaped, tested renderer; never interpolate request-provided filenames into a filesystem root or header.

| Request                                          | Candidate behavior                                                                                                                                                                                          |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Website `/`, `/episodes/<slug>`, `/api/*`        | Proxy to the selected Node image; preserve actual error status and canonical metadata.                                                                                                                      |
| `/feed/podcast` and existing RSS aliases         | Preserve M3 behavior, validators, content type, compression/ETag semantics, and cache policy. No bot challenge or HTML error page.                                                                          |
| Website `/downloads/<public-slug>` GET/HEAD      | One **307**, `Cache-Control: no-store`, to the configured DNS-only media host's `/downloads/<slug>`. Preserve method; do not stream MP3 bytes through the website's Cloudflare connection.                  |
| Media `/downloads/<public-slug>` GET/HEAD        | Serve the mapped persistent MP3 with the exact `Content-Disposition` from `attachment()`, correct type/length, `nosniff`, and no-store. Support partial GET/resume without buffering the full file in Node. |
| Media original MP3 pathname                      | Serve the original canonical bytes for direct playback and RSS; preserve encoding and punctuation. No attachment header on the playback URL.                                                                |
| Website `/wp/wp-content/uploads/<relative-path>` | Serve the mapped artwork file, including both show images and historical variants. Preserve original URLs and image types.                                                                                  |
| Historical `/podcast/...` pages                  | Leave M4's public lookup and one-hop redirect to saved episode pages intact.                                                                                                                                |
| Unknown/nonpublic download or asset paths        | 404, no redirect/fetch/path guessing. Non-GET/HEAD download methods return 405 with Allow.                                                                                                                  |

The browser's `download` attribute alone is insufficient after a cross-origin redirect: the final media response must carry the attachment header. Test actual saves, exact filenames and bytes in Chromium, Firefox, and WebKit. If the owner chooses DNS-only for the entire website, the same URL may directly serve the attachment without the redirect. In either case, deployment configuration must intercept the download namespace completely so an unknown/misconfigured route cannot fall back to M4's Node streaming path through Cloudflare.

For files, verify full 200 GET, bodyless HEAD with full representation length, bounded/open/suffix 206 ranges, valid Content-Range and partial length, and unsatisfiable 416. Test If-Range/conditional behavior against the chosen Caddy build, plus interrupted transfer/resume to an exact checksum. Do not dynamically compress MP3s. Use Caddy's file server rather than promoting the tiny test fixture's range implementation into production.

Cloudflare's current CDN terms constrain large-file/audio delivery on its free website offering. Cache bypass does not remove traffic from the proxy. The proposed topology keeps media bodies on the droplet connection; an exposed media hostname also means the origin IP is public. [Cloudflare application-service terms](https://www.cloudflare.com/service-specific-terms-application-services/)

### TLS, caching, and preview fidelity

Caddy owns certificate issuance/renewal and persists its data across container replacement and host restart. Proposed challenge method: DNS-01 with a pinned Cloudflare DNS module, built in CI, so certificates for the existing canonical hostnames can be obtained before moving public traffic. Its DNS credential is scoped to the relevant zone and kept in the edge service's secret store. Confirm the account's actual DNS arrangement first; if it differs, select and rehearse the appropriate challenge rather than borrowing pfSense-managed certificates. Exercise ACME staging first, then obtain and verify trusted certificates without changing website/media A/AAAA records. [Automatic HTTPS and DNS challenges](https://caddyserver.com/docs/automatic-https)

Use Full (strict) between Cloudflare and the origin when proxying. Bypass shared caching for HTML, APIs, feed/aliases, and downloads initially; preserve the feed's origin policy. Cache versioned app assets and verified artwork deliberately. Do not introduce a wildcard “cache everything” rule, interactive challenges for feeds/assets, restrictive media hotlink rules, or blanket cross-origin isolation headers that break audio. Record existing zone rules and any changes rather than assuming the zone is empty.

Preview must not rewrite canonical content or subscriber identity. Give the preview a noindex response policy; do not submit it to podcast directories. Public preview pages will still contain the saved production artwork/enclosure URLs, which may resolve to WordPress/the old media host until M6. **That playback does not prove candidate delivery.** Validate the new media server separately through its preview hostname, and rehearse exact canonical paths/certificates with an explicit hostname-to-candidate-IP override (for example `curl --resolve` and a controlled browser/device DNS setup).

Record which requests hit the candidate and which still hit legacy production. A preview-only download redirect origin can be selected from trusted deployment configuration without changing any enclosure URL. Run the podcast-client rehearsal on a controlled resolver/profile that reaches the candidate canonical hosts; ordinary public-resolver acceptance must be repeated after M6. An external validator fetching the preview feed proves only the observations it can make at that URL.

## CI, publication, and deployment workflow

Retain the canonical `pnpm verify` command. Add deterministic delivery checks to it after the existing builds/browser checks; those checks must work without cloud accounts, private source media, ACME services, or production DNS. Keep present unit coverage thresholds and run type checking/coverage for new executable deployment tooling as well; do not hide business logic in untested shell templates.

1. **Verify:** On PRs and main, prepare/test/build as now, build the runtime image from that verified `.output`, generate fixture delivery configuration, and test the exact image plus Caddy. Use isolated Compose project names and dynamically allocated ports; clean up only resources created by this run. Produce the image archive and a hashed configuration/manifest bundle.
2. **Publish:** Add a job in the same workflow, depending on successful verification and restricted to a trusted push to `main`. Load/push that exact tested image archive to `ghcr.io/treyturner/nurevolution.net`; record the registry digest and matching release metadata. Give package-write permissions only to this job. Do not rebuild the application for publication, consume a PR-produced artifact in a privileged `workflow_run`, or publish from fork/PR contexts. Pin actions and retain provenance linking digest to commit and verify run. [GitHub workflow event boundaries](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run)
3. **Promote:** An owner-triggered deployment workflow selects preview/production and a validated release digest. Check the release came from the trusted main publication path, retrieve its matching configuration, and use environment-scoped host credentials. The transport and account setup remain D08 inputs. Serialize deployments; do not cancel a deployment halfway through switching state. Production remains a future M6 operation, not an automatic consequence of merging M5. [GitHub environments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)
4. **Deploy:** Under a per-site lock, preflight disk/memory against the measured shared-host budget, verify media readiness and manifest identity, pull by digest, and validate the full candidate edge configuration while the current app remains available. For an existing deployment, confirm that the saved prior release is locally restartable and passes the publication-identity rollback check before replacement. Stop only this site's app and start the candidate at the stable internal endpoint. Check local health, representative SSR/API/feed responses, and matching release metadata within a bounded deadline; then gracefully apply any site route changes and repeat checks through HTTPS. Preflight failures leave the active release intact. Startup/readiness or post-change failures restart the compatible prior image and restore its configuration. On first deployment there is no prior app: stop the failed candidate, restore any changed site routes, and record the environment as undeployed. Record the brief app interruption and recovery outcome; Caddy, media serving, and other sites remain running. Use overlapping containers only when the capacity rehearsal has explicitly established that option.
5. **Rollback:** Select the previously recorded image/configuration/manifest, revalidate it, switch back, and prove the same endpoint/media checks pass. A failed rollback must emit the saved prior/current identifiers and recovery instructions. Do not restore unrelated sites or erase append-only media as part of app rollback.

When a prior release exists, compare public episode/GUID/enclosure sets between the candidate/active and previous release before replacement and again before rollback. If an older image would withdraw newly published episodes or revert protected identity, require an operator-reconciled fallback release that preserves the newer catalog before promotion; do not perform an unsafe automatic downgrade. M5's historical baseline should match across both release records; M6 must retain this check as publishing resumes.

Publication and deployment credentials must be configured outside the repository. The preview and production examples list required variable/secret names with descriptions; private administrative addresses, private keys, ACME state, and backup keys stay out of committed evidence.
