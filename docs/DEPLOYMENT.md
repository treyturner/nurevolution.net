## Release and host contracts

The web build, CI, application image, and deployment/backup helper target Node 24.21.0, pinned in `mise.toml`, `.node-version`, `package.json`, and the digest-bound `Dockerfile`. Delivery verification checks the running container's Node version against the project pin. The helper is a separate host process: the operator provisions its runtime with mise, and the bootstrap verifies and executes the absolute binary recorded in root-owned `node-runtime.json`. Follow the [Node runtime migration](operations/node-runtime.md) before promoting a Node 24 helper. Historical milestone evidence records the versions used at the time.

Deployment and image-identity CI target Docker's containerd image store, matching the droplet. The earlier proposal to switch the droplet to classic `overlay2` was abandoned; maintaining a separate classic-store test path is outside the deployment scope. The `imageId` and `caddyImageId` release fields mean the SHA-256 of the original Linux/amd64 image configuration bytes, which bind the runtime configuration and filesystem layer digests. Docker's displayed `Id` can instead identify a manifest and is not a portable comparison. Verification reads the configuration from the tested export; publication checks the loaded image the same way. The host checks the actual local image configuration, the exact registry reference, and the application's source label. The shared edge is checked using its running container's actual image reference, with the existing binary/build-policy fallback for an independently rebuilt edge.

Identity checks use Docker's platform-specific save operation and the host's `tar` command. They stream one image at a time to a private temporary directory on the selected site/release filesystem, read only bounded manifest/configuration output into Node, and remove the export on success or failure. Host exports use `/srv/nurevolution`, which is covered by the disk preflight; Ubuntu 26.04 mounts `/tmp` in RAM on this droplet, so it must not hold image exports. Allow space for one uncompressed image in addition to the normal release/media reserve. The target is Linux/amd64; image indices must be exportable for that platform. The single CI identity job requires containerd and exercises real save/load/push/pull cycles, including the manifest-versus-configuration ID regression, before publication.

`pnpm verify` ends with the local Docker integration suite, `pnpm test:delivery`. The suite builds the application image from the already tested `.output`, builds Caddy 2.11.4 with the pinned Cloudflare module, exercises them with tiny original fixtures, and exports the exact images plus metadata in `.local/delivery/artifacts/`. It removes its temporary containers, network, and fixture volume afterward. This is local verification, not a production deployment; it does not contact cloud accounts or legacy media. Runtime containers are non-root, read-only, and bounded to 384 MiB in the local check; that is an initial application limit to measure on the shared 1 GB host, not proof of host capacity.

Use the workspace's preconfigured Docker CLI connection through its mounted Unix socket. Run `docker info` to verify daemon access; inspect the Docker context and any `DOCKER_HOST` or `DOCKER_CONTEXT` override if it fails. Socket paths depend on the workspace. The tests use this connection to build images and manage their temporary containers. The delivery runner copies fixtures through isolated Docker volumes, so the daemon need not share workspace paths. Do not use the public droplet as an ordinary CI Docker daemon.

HTTP access to the test containers is separate from Docker socket access. The runner publishes ephemeral ports on `127.0.0.1` by default and sends HTTP/browser requests to them from the workspace. Leave `NUREVOLUTION_DOCKER_ADDRESS` unset when those ports are reachable at the workspace's localhost. If the Docker daemon runs in a separate network namespace, set that variable to a verified IPv4 interface on the Docker host that the workspace can reach. The runner uses it both to bind the temporary published ports and to construct test HTTP URLs; it does not select the Docker daemon or enable a TCP Docker API.

Resolve and verify the address for the current workspace instead of copying a private IP from a previous run. In workspaces with a Docker service named `docker`, `getent ahostsv4 docker` shows its current IPv4 address; confirm that service hosts the daemon exposed by the socket before using it. Private IPs can identify unrelated containers on other networks. Historical verification records retain the addresses used for those runs.

The release bundle contains `release.json`, `manifest.json`, `configuration.json`, `deploy.mjs`, `renderer.sha256`, and delivery evidence. Release records bind the source SHA, successful verification URL, both image IDs/digests, and exact manifest/configuration hashes. Configuration binds the Compose template, complete `deploy.mjs` executable hash, and renderer/Caddy build fingerprints. The deployment tool is bundled before configuration hashing; publication and release verification reject changed executable bytes. The host deployment record retains the accepted operator profile with a hash of its canonical JSON, plus a separate rendered edge configuration hash, because hostnames and measured resource limits belong to the environment. Recovery acceptance uses that saved profile's website and media origins even if the next deployment changes them.

PR jobs have no cloud secrets or publication privileges. The publisher runs only after a successful trusted main push, loads the tested archives, verifies image IDs, and pushes without rebuilding. Release artifacts are retained for 90 days. Keep current/previous bundles on the host and in the independent backup before artifacts expire; retain their GHCR images. Missing/expired artifacts require a new verified main publication before workflow promotion, rather than bypassing provenance checks.

## Initial host preparation

M5 configures nurevolution only. Preserve the shared Caddy edge and separate application network, configuration, secrets, and release state so other sites can be added later. Their domains, deployment, and resource planning are outside M5; assess available capacity when adding each site. Existing disposable isolation checks demonstrate compatibility without requiring another real site during this milestone.

Create the host with DigitalOcean's plain Ubuntu 26.04 LTS x64 image (`ubuntu-26-04-x64`). Inventory region, installed OS, existing containers, proxy ports, DNS A/AAAA/proxy settings, disk/inodes, free memory, firewall, SSH transport, and other workloads before installing anything. Capture these in [the evidence template](milestones/evidence/M05-deployment-record.example.json). Follow [Docker's supported Ubuntu installation](https://docs.docker.com/engine/install/ubuntu/), using its stable repository for Ubuntu 26.04 (`resolute`), and account for published-port firewall behavior. Provision the [mise-managed Node runtime and bootstrap](operations/node-runtime.md) with root ownership and read/execute access for `nurevolution-deploy`. No pnpm, application build dependencies, or compilation is needed on the host. The site's tooling no longer uses the global `/usr/local/bin/node`; keep any older runtime until its other consumers and recovery requirements have been checked.

[Host bootstrap evidence](milestones/evidence/M05-host-bootstrap.json) records Docker Engine 29.8.0, Compose 5.5.1, Node 22.23.2, the dedicated `nurevolution-deploy` operator with verified SSH access, and the `nurevolution-site` network. The Cloudflare account token passed verification and a temporary TXT create/read/delete check. Runtime preparation does not establish application, certificate, or capacity acceptance.

Create an operator-owned `/srv/nurevolution` with `incoming/`, `tooling/`, `releases/`, `state/`, and `media/`. Keep it outside every web root. Install the reviewed [stable bootstrap and host helper](operations/tooling-bootstrap.md) once. They fetch and verify the exact release artifact using GitHub provenance, retain versioned tooling, and select its executable and renderer together before deployment. The host continues to check both installed and executing code against `configuration.toolingSha256`, as well as the renderer fingerprint. Dependency-only executable changes no longer require manual installation. The bootstrap and wrapper are root-owned; release caches remain operator-owned. Record the actual shared Caddy container name in `/srv/nurevolution/edge-container`.

Copy [profile.example.json](../deploy/profile.example.json) to `/srv/nurevolution/profile.json` and measure its resource settings. The host preflight accounts for reclaimable memory from the current app when replacing it; keep room for OS/Docker/Caddy, any services actually present, uploads, and backups. Record remaining headroom for future capacity decisions. Measure concurrent SSR/feed requests and media transfers, startup, and backup peaks. The baseline runs one app instance and retains the prior image on disk. Preserve the accepted production profile during subsequent promotions.

Create the dedicated `nurevolution-site` Docker network. An existing shared edge should join that network and receive the site's read-only media mount; add this site's route without replacing other sites. For a fresh host, [edge.compose.yaml](../deploy/edge.compose.yaml) and [initial.example.json](../deploy/caddy/initial.example.json) are starting points. The edge configuration lives in `/srv/edge/config/caddy.json`, with its `https` server and other routes retained by deployment. Mount the configuration **directory**, so atomic file replacement is visible inside Caddy. Persist `/srv/edge/data` and `/srv/edge/state`.

While the public-path QUIC incident is under investigation, production promotions explicitly set the `https` server's protocols to `h1` and `h2` and remove per-listener protocol overrides. This is the one deployment-managed exception to preserving operator-owned listener settings; it affects every route sharing that server, while other servers and TLS settings remain unchanged. The site sends `Alt-Svc: clear` to retire cached alternatives. The separate QUIC test droplet keeps HTTP/3 enabled. See [HTTP/3 mitigation and verification](operations/http3.md) for activation, scope, and recovery.

Pin `CADDY_IMAGE` to the published Caddy digest from the release record. Configure the zone-scoped DNS token outside Git. Complete [TLS rehearsal](operations/tls.md) before exposing production. The application helper never restarts or upgrades the shared edge; an identical tested image is accepted directly, and independently rebuilt images are accepted only when both the binary SHA-256 and pinned build-policy label match the verified release. A changed binary/build policy requires separate operator reconciliation with the other sites accounted for.

## Media, promotion, and rollback

The application uses the accepted profile’s `webOrigin` and `mediaOrigin` for browser artwork and audio requests. The host passes them through Compose as `NUXT_PUBLIC_WEB_ORIGIN` and `NUXT_PUBLIC_MEDIA_ORIGIN`; rollback restores the previous profile’s values. Canonical content, API records, RSS enclosures, and page identity links remain unchanged. Production artwork comes from `nurevolution.net` and audio from `podcast.nurevolution.net`. Local/workspace development may override browser delivery origins without adding a hosted deployment environment. The bootstrap selects the matching verified release tooling, including the Compose variables required by that release.

Do not grant local-network permission to make media work. Before cutover, the owner’s local DNS mapped the production website and podcast host to pfSense (`192.168.1.1`), so embedding their URLs from the former rehearsal website triggered [Chrome’s local-network access restriction](https://developer.chrome.com/blog/local-network-access). The owner removed the apex, `www`, and podcast overrides during M6; ordinary LAN DNS and fresh-browser media loading then passed. Browser tests continue to require the configured delivery hosts. RSS intentionally retains canonical media URLs. Preserve the old overrides privately for fallback; do not reinstate them during normal production operation.

Use [the media procedure](operations/media.md) to audit, stage, upload, and verify all 156 assets. Application images contain no MP3s or private WordPress source. Keep draft-only assets out of public mappings. Future-dated published episodes are rejected until M9 can coordinate the static maps with scheduled visibility.

Configure only the GitHub environment `production`. It needs variables `HEADSCALE_URL`, `DEPLOY_HOST`, `DEPLOY_USER`, and `DEPLOYMENT_ENABLED=true`, plus secrets `HEADSCALE_AUTH_KEY`, `SSH_PRIVATE_KEY`, and independently verified `SSH_KNOWN_HOSTS`. The current workflow uses SSH port 22. Restrict deployment key forwarding and use a dedicated operator account with only the needed host access. Docker access is privileged host access; the helper's validated arguments do not turn an unrestricted Docker account into a security sandbox. Resolve runner access before opening firewall ports.

The DigitalOcean firewall still permits public SSH only from the owner's address. The droplet is enrolled at `100.64.0.1`; disposable runners verified the operator identity and SSH access through the self-hosted relay, and could not reach its listening HTTPS port. The branch workflow joins Headscale only after release verification, uses the pinned repository-owned userspace client with temporary credentials and in-memory state, verifies the SSH operator before transfer, and logs out after the job. Set `HEADSCALE_URL=https://headscale.treyturner.info`, map the original pinned host public key to the private address, and follow [environment configuration and key rotation](operations/headscale.md#github-environment-and-rotation). [The production promotion passed](https://github.com/treyturner/nurevolution.net/actions/runs/34720835192). The owner accepted mobile testing for launch; the remaining client and boot/recovery observations are listed in M6.

Keep production's `DEPLOYMENT_ENABLED=true` and `CUTOVER_ENABLED=true`, its accepted profile, and `/srv/nurevolution/production-enabled` in place. The profile and host helper reject every environment other than production. In the manual workflow, supply the successful main Verify run ID and its full source SHA; the target is fixed to production. The workflow validates the source run and release hashes, checks the installed bootstrap protocol, and sends a temporary Actions-read token over SSH stdin. The host independently verifies the successful main run and GitHub artifact digest before staging/executing release tooling. It preserves current tooling for rollback, creates a fresh `incoming/<run_id>-<run_attempt>` directory, and invokes the exact candidate tool. Reruns preserve earlier attempts for diagnosis. Complete the [one-time bootstrap installation](operations/tooling-bootstrap.md) before the first promotion using this workflow. A helper/profile environment mismatch fails before deployment.

Deployment acquires the site and shared-edge locks, audits media and capacity, pulls by digest, checks image identity, and validates the complete candidate proxy configuration before interrupting the app. It journals the candidate/prior records under `state/production/`, replaces only the app, checks readiness, and reloads site routes. HTTPS acceptance checks health/SSR/API/feed plus representative enclosure HEAD/range, attachment/redirect, and artwork delivery before committing the current record. Failures restore a compatible prior image/configuration from the same environment; first-deployment failure leaves no app selected. App pages/feed can be briefly unavailable; the edge, media, and other sites remain running. Follow [rollback and interrupted-deployment recovery](operations/rollback.md).

Both deployment and rollback protect the already public episode/GUID/enclosure set. Until M9 supplies a content-preserving fallback strategy, the automatic transaction requires matching subscriber identities in current/candidate releases. Initial deployment is supported; an image that adds/removes published episodes requires a reconciled fallback procedure, not bypassing the check.
