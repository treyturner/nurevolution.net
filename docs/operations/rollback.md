# Rollback and interrupted deployment

The operator CLI retains `current.json`, `previous.json`, a durable `pending.json` while a change is underway, and `last-attempt.json` beneath `state/production/`. The site-wide lock remains `state/deploy.lock`; an unresolved journal anywhere in the active state tree blocks deployment. State-directory creation, file replacement/removal, and lock creation/removal flush their containing directories before reporting completion. Journal removal is durable for deployed, restored, and undeployed outcomes; a failed directory flush is reported as an error. Unscoped records from the prototype require explicit environment reconciliation before promotion. Keep current/previous images locally and retrievable from GHCR, and retain their bundles independently. The rollback record includes app image identity, canonical manifest, Compose template, the accepted host profile, and configuration/profile hashes. The profile hash covers its canonical JSON serialization. Missing, inconsistent, or cross-environment saved profiles stop promotion before Docker operations; reconcile prototype state against the actual accepted configuration before proceeding. No whole-droplet snapshot restore is part of an app rollback.

To revert an accepted release using the same checks and locks:

```sh
python3 /usr/local/lib/nurevolution/bootstrap.py rollback
```

This selects only the previous record for the profile's environment and refuses a catalog downgrade that would withdraw published episodes or change GUID/enclosure identity. The [stable bootstrap](tooling-bootstrap.md) verifies the retained target artifact and selects its exact executable and renderer, so tooling rollback works offline even when executable hashes differ. Every promotion retains the prior tool before changing the app. Reconcile a newer catalog into a compatible fallback when necessary. The host hashes both its installed tooling file and the executing bundle against the release configuration. No command automatically prunes media, images, volumes, other sites, or the shared edge.

## Publication snapshots

Publication-capable releases bind a version 1 snapshot inventory into the digest-verified configuration. The tested image contains canonical content, playback indexes and headers, episode artwork, and thumbnails under `/app/.output/publication`. After verifying the image, the host extracts the snapshot into `publications/<source-commit>`, validates every filename and checksum, rejects symlinks and extra files, and confirms the catalog produces the release's media manifest. Snapshots are mounted read-only at `/publication`; the app uses that catalog and playback data and serves generated artwork from the same snapshot. A configured but missing or corrupt snapshot fails verification rather than falling back to bundled content.

Before adding an episode, deploy this support code with the public catalog unchanged and verify production. Keep new episode content absent or draft during that support release. The first support release can recover to the legacy application because its public subscriber set remains unchanged. Its new metadata is withheld from the website/feed and media routes. Only then publish the episode in a second verified release with its original artwork uploaded and its generated derivatives committed.

For subsequent promotions between capable releases, the saved fallback combines the previous verified code image with the candidate's verified publication snapshot. Its original code release/manifest/configuration remain intact; a separate `publication` reference identifies the snapshot release. Both forward deployment and recovery preserve every already-public GUID/enclosure. Before interruption, a network-isolated container runs the fallback code with the new snapshot and checks all public episode pages, API identities, RSS, chapters, thumbnails, and retained feed artwork. The probe needs additional free memory while the live app is running; insufficient measured headroom blocks promotion before downtime. Failed probes are removed and leave the public app untouched.

The durable journal records the reconciled fallback before stopping the app. Automatic recovery restores its code, snapshot, and compatible media/download routes. Explicit code rollback carries the same publication reference forward. The bootstrap independently verifies both referenced retained artifacts before selecting rollback tooling. Retain both code and publication artifacts/images, the extracted snapshots, and state together. Backups include `publications/`; do not prune snapshots that current, previous, or pending records reference. A legacy rollback target that would withdraw a newly published episode is rejected.

After upgrading the root-owned bootstrap from this repository's verified support commit, check both retained artifacts with the bootstrap before the first publication. Root bootstrap installation remains an operator action separate from changing versioned release tooling. New-content publication is complete only after public acceptance and a successful backup containing the new media and publication snapshot.

A failed health/HTTPS/media check restarts the prior app for the same environment with its accepted memory limit and readiness deadline, then restores the edge route. Preflight reserves enough headroom for both the candidate and the saved fallback, so lowering the candidate limit cannot bypass recovery capacity checks. Acceptance includes a representative enclosure HEAD/range request, its download redirect and attachment metadata, and an artwork probe before committing state. A failed first deployment leaves the app undeployed. Failed recovery retains the journal and reports candidate/prior identifiers. Host validation uses a separate `candidate.compose.yaml`; a rejected candidate cannot replace the active `compose.yaml`. The active Compose file changes only after the recovery journal is written. A corrected retry can therefore inspect the still-running app through its accepted configuration. The transaction updates the current record only after acceptance; inspect the attempt record and actual containers rather than inferring success from an incoming bundle.

When `profile.json` changes website or media hostnames within an environment, candidate acceptance uses the new addresses and automatic recovery checks the addresses saved with the prior release. Keep the prior DNS/TLS paths reachable until the change is accepted. Automatic recovery leaves the proposed `profile.json` available for correction or retry; it does not replace the operator's file. An explicit rollback command deploys the selected earlier release using the current operator profile.

After a killed process or host interruption, the next deployment refuses an existing lock or journal. Confirm there is no active deployment, backup, or other edge change. Save the pending/current/previous records and current edge configuration. Inspect which image is actually running and whether the candidate route became active. Select the compatible known release, restore its exact app/route with the recorded profile, and repeat local/HTTPS/feed/media checks. Only then archive the interrupted journal, reconcile `tooling/active` to the recovered release, and remove stale bootstrap/site/edge lock directories and owned `.pending` or tooling `.next` files. The bootstrap lock is `/srv/nurevolution/tooling/deploy.lock`; do not remove it while a bootstrap operation is active. Do not remove a live lock or simply rerun through an unresolved journal.

Every shared-edge editor must honor `/srv/edge/config/deploy.lock`. Deployments preserve unrelated routes/settings, except for the explicit [production HTTPS protocol policy](http3.md), and reload gracefully; unrestricted concurrent manual edits are outside the locking contract. Record the app interruption interval and prove an unrelated sentinel endpoint plus media remain available during ordinary app replacement.

The lock is a **temporary directory**, acquired atomically with `mkdir` without `-p`. A writer must stop if acquisition fails, keep the directory throughout its edge operation, and remove only the directory it acquired after the operation completes. Using `flock`, `touch`, or shell redirection at this path implements a different protocol: a regular file left behind blocks the bootstrap and release tools even when no advisory lock is held. Other sites' deployment scripts and manual edge edits must use the same directory protocol.

When investigating a blocked backup, inspect the service journal and the exact lock paths before changing MinIO or removing a marker:

```sh
journalctl -u nurevolution-backup.service -n 50 --no-pager
stat /srv/nurevolution/tooling/deploy.lock /srv/nurevolution/state/deploy.lock /srv/edge/config/deploy.lock
lsof -- /srv/edge/config/deploy.lock
```

Run these in the droplet's root shell for complete journal and process visibility. Missing paths are normal when their locks are not held. An empty `lsof` result alone does not prove a directory lock is stale: confirm there is no active deployment, backup, edge edit, or unresolved journal. Preserve the marker's metadata before quarantining a proven inactive incompatible file or clearing a stale directory. Investigate which writer created it and correct that writer's locking procedure to prevent recurrence. A failure at the bootstrap lock check occurs before restic contacts MinIO; MinIO health and backup destination capacity are separate checks.

## M8 feed-resource compatibility

Before a release advertises episode artwork or Podcasting 2.0 chapters, deploy and verify the resource-support release and retain its exact artifact as the fallback. That release serves chapter endpoints and generated artwork while retaining the old RSS fields. Once clients have seen the new references, every rollback target must keep those endpoints and all previously advertised artwork files. Old chapter version hints resolve the current eligible chapter data; image paths are immutable and must not be overwritten or removed. The deployment tool's GUID/enclosure guards do not establish this resource compatibility by themselves. Verify it explicitly when choosing the fallback. See [the ordered rollout](../FEED-VALIDATION.md#m8-resource-support-and-rollout). The phased M8 rollout completed on 2026-09-18. Production release `4ca5c3d` retains verified support release `4d0100c` as its compatible fallback; both bundles passed the bootstrap check. See the [rollout record](m8-rollout.md) for full commit identifiers and results.
